# 検索 domain 管理語彙

最終更新: 2026-09-20

## 定義

`domain` は、再利用する段取り全体を表す、有限で平坦な活動分類である。検索時の第一段階で異種の活動を除くために使う。

「管理語彙」とは、次の条件をすべて満たすものを指す。

- 有効な値は、レビュー済みのカタログに明示されたものだけである。
- LLM、利用者の自由入力、保存済み行の `DISTINCT domain` は、カタログを自動追加・変更しない。
- 表記揺れや旧称は alias として既存の値へ解決し、別 domain として保存しない。
- 値の追加、統合、廃止は、カタログ変更としてレビューし、履歴と置換先を残す。
- 検索と保存は、同じバージョンのカタログを参照する。

したがって `domain` はタグではない。地域、制度、対象者、同行者、道具、サービス名、個別タスク、手段、時期を増殖させる場所でもない。これらは `required_tasks`、`required_context`、`context_text`、embedding で扱う。

## 分類単位

分類は「その段取り全体は何の活動か」で決める。部分的な手続きでは決めない。

| 入力・段取り | domain | domain にしない情報 |
| --- | --- | --- |
| 子どもの転校を伴う引っ越し | 引っ越し | 子ども、転校、東京、名古屋 |
| 引っ越しを伴わない転校 | 学校手続き | 学校名、在学証明書 |
| 猫を連れて旅行する準備 | 旅行準備 | 猫、航空会社、行き先 |
| LINE を含む機種変更 | 端末移行 | LINE、iPhone、Android |

境界は次の順で判定する。

1. タイトルと主要タスクの過半が属する、利用者の最上位の活動を選ぶ。
2. 明示された上位活動の中にある個別手続きは、別 domain へ移さない。
3. 上位活動がなく、個別手続き自体が段取り全体なら、その活動の domain を選ぶ。
4. 複数の上位活動が独立して混在する場合は、無理に新しい複合 domain を作らず、公開前に分割を求める。

## カタログ項目

論理上の各項目は次を持つ。

| 項目 | 意味 |
| --- | --- |
| `id` | 変更・再利用しない機械識別子。例: `moving`。 |
| `label_ja` | UI と現行 BQ `domain` に使う正規表記。例: `引っ越し`。 |
| `description` | 含める活動の一文定義。 |
| `includes` | 境界判断に使う代表例。 |
| `excludes` | 似ているが別 domain になる反例と置換先。 |
| `aliases` | 入力解釈用の表記揺れ・旧称。保存値には使わない。 |
| `status` | `active`、`draft`、`deprecated` のいずれか。検索・保存候補は`active`だけ。 |
| `replacement_id` | 廃止時の移行先。統合できない場合は空。 |

現行 BQ の `domain STRING` は当面 `label_ja` を保存する。カタログを導入するためだけにスキーマ移行は必須ではない。ただし、表示名の変更が必要になった時点で `domain_id` 列へ移行する。

## 追加・統合の受入条件

新しい domain は、次をすべて満たす場合だけ追加する。

- 既存 domain の文脈差や一部タスクではなく、独立した最上位活動である。
- 既存 domain に入れると、検索のハードフィルタとして継続的に誤配信が起きる。
- `required_tasks`、`required_context`、`context_text` で表現しても境界を保てない。
- 含む例と除外例を少なくとも一つずつ定義できる。
- 既存データの移行先と検索評価ケースを同じ変更で用意できる。

単なる表記揺れ、地域差、対象者差、製品・サービス差、制度差だけなら追加しない。活動の境界が同じ値は統合し、alias か文脈として扱う。

有効 domain は「数十個」に収まることを設計上の期待値とする。40個を超えたら上限エラーにはせず、まず分類軸の混在と細分化をレビューする。件数増加を前提に無制限な動的分類へ戻さない。

## 未分類と保存

LLM は有効カタログから一つを選ぶか、`null` を返す。該当なしの場合に自由語や検索可能な「その他」を保存してはいけない。

- 検索: `null` は該当 domain なしとして結果を返さない。
- 公開: カタログに該当しなければ公開を止め、分類の見直しまたは新 domain のレビューへ送る。
- 廃止値: 読み取り時に `replacement_id` へ解決し、バックフィル後に旧値を検索候補から外す。

## 実装上の不変条件

- 検索 LLM の候補は `active` なカタログ項目だけにする。
- 保存 API はカタログ外の値を拒否する。UI の自由入力だけを信頼しない。
- alias は入力解釈にだけ使い、BQ へ保存しない。
- BQ は正規値で cluster し、検索条件を `domain = @domain` の直接比較にする。現行の `NORMALIZE_AND_CASEFOLD(domain)` はカタログ移行中の互換処理であり、cluster pruning を阻害し得るため残さない。
- 検索に期間条件がない限り、`created_at` partition は domain 管理の代替にならない。
- 新規・廃止・alias 変更には、保存検証、検索解釈、代表クエリの回帰テストを付ける。

## 現行実装（2026-09-20）

- 定義元は`web/src/lib/domain-catalog.ts`。30件すべてが上記8項目を持つ。
- 保存時LLMはactiveな正規labelだけを候補にし、API schemaもカタログ外値とalias保存を拒否する。
- 検索候補はactiveな30件と、公開Revisionに実在する値との積集合で作る。BQの`DISTINCT domain`は語彙定義に使わない。
- 検索SQLは正規labelの`domain = @searchDomain`で比較する。
- 初期データは`web/data/managed-domain-seeds.mjs`に30 domain × 3 Revisionとして保持し、`web/scripts/seed-managed-domain-corpus.mjs`で明示したproject/datasetだけへ冪等登録する。
- 境界評価は各domain positive 2件・negative 2件の合計120件で、実Vertex判定120/120合格。

旧`task_list_entries`の3件は所有者の公開同意を推定できないため、新公開Revisionへ自動移行していない。legacy検証データとして新検索経路から除外し、管理語彙の入力元にも使わない。
