# Cuckoo Cue: 思想と実装の32項目監査

監査日: 2026-09-13。ユーザー提示の32項目の番号・観点を維持する。

本書は修正前の監査記録。後続のユーザー指示により、実装・再レビューはWebに限定し、Android/Widgetは対象外とした。下記の表示欠落・既存由来リンクはその後修正している。最新の変更・受入結果は[Web体験仕様21節](web-experience-spec.md#21-webの文脈と由来導線の修正2026-09-13)を参照する。32項目から新しいモデル・検索方式の追加を承認されたものとして扱わない。

## 範囲と結論

現行design_v2、Webの実装、AndroidのRun/Cuebook受信・保存、既存のAPI記録とスクリーンショットを照合した。新しいデータや想定利用者は作っていない。本番再試験、利用者観察、新しい機能・データモデルの実装は行っていない。

**「実行可能な段取りを借りる」「完了内容を整えて公開する」「Shelfを固定版でコピーして編集する」は接続されている。一方、「文脈から知識のまとまりを見つけ、由来を理解し、自分の経験を重ねて再利用する」全体は成立確認できていない。** 主な理由は、Shelf文脈と検索の非接続、閲覧経路による情報欠落、実行後の由来の断絶、Android原本同期の未接続である。

「構造成立」はコード上の接続・制約を確認した意味であり、使いたくなることの実証ではない。「一部」は成立部分と欠落を併記する。「仕様差」は32項目の期待と現行の合意が異なること。「未確認」は既存の証拠で評価できないこと。成立率に合算しない。

## 実際の接続

| 段階 | 保存・参照される情報 | 体験に効く点と境界 |
| --- | --- | --- |
| 公開検索 | Revisionのtitle/tasks/domain/context_text/grouping。検索文とMemory Bank属性を混合したembeddingで順位付け | Shelf名・Shelf.context・参加ID・著者人気・自分の非公開原本は候補選択/順位付けに入らない。全文検索語のいずれか一致 **または** domain一致で候補となる |
| 関連Shelf表示 | ヒットしたRevision IDをShelf.itemsから逆引き | 内容の配置関係が根拠。文脈が近い別Shelfを探す処理ではない。検索結果ではShelf名のリンクだけ |
| Shelf閲覧・参加 | Shelf.contextと固定Revision一覧を表示。users/{uid}.shelf_idsを追加/除去 | 参加は再訪用の参照。本文・原本の複製、投稿権限、検索の個人化は発生しない |
| Shelf全件コピー | 新Shelf、元Shelf ID、同じRevision IDと配置順 | 本文はコピーしない。コピー先のcontext/配置を独立変更できる。元の後続変更には追従しない |
| 借用・日程確定 | BQの私的Cuebookにorigin_revision_id。Firestore Runにsource_cuebook_idとsource_task_id | 参加不要。Shelfから使っても借用APIにはRevision IDだけが渡り、選択元Shelfの文脈は引き継がない |
| Android実行・同期 | Run IDを維持してRoom受信。変更後snapshotをFirestoreへ送信 | 原本を自動更新しない。現行受信は新規Runのみ。BQの私的Cuebook本文をRoomに取得・同期する処理とは別 |
| 完了履歴から整える | 完了Runの最終タスク内容・優先度・最終予定日程をdraft化 | 削除済みタスクや変更理由の履歴はない。これは「完了した内容でよい」という合意と整合する |
| 私的保存・公開 | 新Cuebook、そこから不変Revisionを作り、自分のShelfへ配置 | 新Cuebookに元Run参照を保存しない。公開版は新原本まで追えるが、その前の実行へのつながりは失う |

## 優先して扱う具体的なギャップ

### 1. 公開リストの入口によって、文脈とShelfへの導線が消える

検索結果とその詳細モーダルにはcontext_textと関連Shelfがある。一方、`?revision_id=...`の個別公開版画面はタイトル・公開日・タスク・利用ボタンだけ。公開成功後や共有URLから開いた人は、どんな状況に向く内容か、他にどんなリストが同じ棚にあるかを確認できない。

これは追加モデルの必要性ではなく、既存の情報・実配置参照の表示経路の欠落。web-experience-spec冒頭19行の「公開リスト詳細では関連グループへのリンク」にも届いていない。優先修正対象。

根拠: [検索結果コンポーネント](../web/src/components/search/search-result.tsx) 34/77/88行、[個別公開版](../web/src/components/public-revision.tsx) 24行、[公開版projection](../web/src/lib/shelves.ts) 12/27行。[既存PC画像](review-screenshots/web/residual-fixes/revision-desktop.png)でも欠落を確認。画像はfixture表示であり本番利用記録ではない。

### 2. Shelfの文脈は保存できるが、その文脈が発見と借用に接続していない

検索SQLのembedding対象もsearch_textも公開Revision由来。Shelf.contextを変更しても検索候補・順位は変わらない。関連Shelfは実配置で逆引きされるため、棚に既に置かれた他の段取りへ進む道はある。つまり「Shelfが機能していない」のではなく、**文脈によって棚を独立発見することはできず、リストを経由することが前提**。

この制限はD4で明示採用済み。類似Shelf推薦を勝手に追加すべきではない。ただし32項目の#5/#8/#11が意図する価値を、現行方式だけで満たしたとするのも誤り。既存の関連Shelfリンクにcontextを見せることと、検索アルゴリズムへShelf.contextを入れることは別の変更として扱う。

さらに同じRevisionを違う文脈のShelfから借りても、作る私的Cuebookのenrichmentは同じRevision由来。RunにもShelf参照はない。棚で与えられた意味を後から辿ることはできない。これを保存するならモデル・契約の判断が必要で、今回追加しない。

根拠: [検索SQL](../web/src/lib/bigquery.ts) 130/189行、[借用](../web/src/lib/cuebooks.ts) 58行、[Shelfの利用ボタン](../web/src/components/shelf-detail.tsx) 196行、[D4](web-experience-spec.md)。

### 3. 由来は「IDがある箇所」と「途切れる箇所」が混在する

fork元Shelf IDと借用元Revision IDは存在するが、Webでは元を開く表示に接続されていない。この部分は既存モデルで改善できる。ただし元の私的Cuebookを他人に開示するリンクを作ってはならない。

完了Runから新原本を作ると、タスクIDを新規発行し、保存PUTはtitle/tasks/enrichmentだけを送る。新規Cuebookのorigin_revision_idはNULL。元Runやそのsource_cuebook_idを辿る参照は保存されない。古いRunを残しているだけでは、新原本がどのRun由来かを確定できない。

forkは現在の固定Revision配置を保存するが、元Shelfのコピー時状態の永続履歴やその後の差分を持たない。参照ID表示、実行由来の保持、差分履歴は別要件。後二者は32項目との設計ギャップとして扱い、新カラムを勝手に足さない。

根拠: [完了Run変換](../web/src/lib/synced-run.ts) 34行、[履歴を開く/私的保存](../web/src/components/cuckoo-cue-web-app.tsx) 513/548行、[新規原本](../web/src/lib/cuebooks.ts) 38行、[fork SQL](../web/src/lib/shelves.ts) 126行。fork元IDのWeb参照は型宣言・保存/取得にあり、描画利用は確認できない。

### 4. 原本を育てる個人利用は、WebとAndroidでまだ一続きではない

Webで原本を保存し、そこからRunを作ってAndroidが実行する経路はある。しかしRunSyncClientが受信するのはRun/Taskだけで、BQ Cuebook本文をRoomへ取り込む処理はない。Androidの私的原本作成・一覧はRoomを使う。Webで整えた原本がそのままAndroid原本一覧へ現れるとは言えない。

既存要件G03/D10と設計v2の「同じ私的原本を共有する」に対する未接続。Web検索から同じRunを受信したE2E成功で解消してはいけない。Web単体の追加画面ではなく、アプリ全体の再利用サイクルの残件として優先する。

根拠: [Run受信](../android/app/src/main/java/app/cuckoocue/data/RunSyncClient.kt) 48/73行、[Android原本保存/Run作成](../android/app/src/main/java/app/cuckoocue/data/CuckooRepository.kt) 55/106行、[既存残件G03](web-experience-spec.md) 585/888行、[設計](design_v2.md) 102/204/345行。

### 5. 「現在の状況に合う」を既存の検索結果が反証している

既存記録の「同じ区内で猫と近距離の引っ越し」は、profileなしでは近距離版が上、profileありでは長距離版が上。「子どもの転校を伴う東京から名古屋への引っ越し」も、profileありで転校版より猫の長距離版が上に来た。さらに過去の「ロンドン在住時」が属性では「ロンドン在住」になった。

6件内の期待1位はprofileなし6/6、あり4/6。ただし全検索結果は4〜23件あり、この数値は全corpusに対する精度ではない。期待1位には試験作成者の判断も含む。それでも、同じ検索文でprofile有無によりこの順序が逆転した事実は残る。成功率の一般化ではなく、現在の条件が過去属性に負ける既存の反例として扱う。

profile混合方式の変更、重み、閾値追加をここで承認しない。まず既存G01/C08を「品質上の懸念未解消」のまま維持する。

根拠: [既存の生データ](review-screenshots/web/residual-fixes/data-evidence.json)のsearches/profileAttributes/operations、[embedding入力](../web/src/lib/task-list-embeddings.ts) 76行。

### 6. 参加・fork後に「知識が育つ」責務を誤認しない

参加は参照だけなので、他の参加者の実行・完了によって棚の中身は増えない。所有者が自分で新公開版を置くか、既存公開版を追加する必要がある。参加者も自分の棚をforkして育てられるが、元棚への自動還流や派生一覧の導線はない。

これは共同編集を避ける合意と整合する。しかし「参加すると同Contextの経験が自然に蓄積される」を既に実現したとは言えない。再訪の価値は、更新量ではなく、所有者が整えた構成を再び使えることも含めて評価すべき。新着通知・Feed・参加者投稿を不足機能として自動追加しない。

根拠: [membership](../web/src/lib/memberships.ts) 4行、[所有者制御](../web/src/lib/shelves.ts) 69/95行、[Shelf UI](../web/src/components/shelf-detail.tsx) 132/167行、[再訪画面](review-screenshots/web/shelf-journey/06-revisited-desktop.png)。

### 7. 合意していない機能を「未実装バグ」にしない

実行回数、link/context限定公開、AI初期タスク供給、手書き専用機能、自分の非公開経験を含む統合ランキングは現行と32項目に差がある。採用するかの判断が必要で、今回の監査を実装指示へ読み替えない。Experienceも独立Entityにしない。公開グループ全件一覧、private Shelf、Revision自動更新を再提案する根拠にはならない。

## 次の判断の順序

1. **既存モデルのまま直せる意味情報の欠落**: 個別公開版のcontext/実配置Shelf導線、保存済みのfork元・借用元への表示。#5/#10/#13/#23/#27に対応。由来の私的原本は公開しない。
2. **合意済みサイクルの未接続**: Android原本同期G03/D10。#1/#22をRun同期だけで完了扱いにしない。
3. **既存の品質反例**: 検索G01/C08を未解消として扱う。数値調整や追加データで問題を隠さない。
4. **設計上の差を判断する**: Shelf文脈を閲覧時だけに閉じるか、完了Runから新原本への由来を必要とするか。ここは既存表示の補完とは違い、検索/保存契約の変更となりうる。追加実装前に明示する。
5. **証拠が足りない価値は未確認のまま残す**: #6/#11を新しい都合のよいShelfや利用者で成功にしない。現状は「再訪・コピーできる」まで。補完的発見、繰り返し利用、初見理解を示す既存観察記録はない。

設計文書の初期D表・モック記述には、後続節で変更済みの記述が残る。例えばweb-experience-spec 135行の「文脈はShelfから取得」は現在のRevision.context_text検索と異なる。今回の実装判定はdesign_v2の物理契約16節と実コードを照合し、古い記述を新規要件として復活させていない。文書の記述競合自体は残っている。
